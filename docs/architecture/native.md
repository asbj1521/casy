# The native iPhone app: how it is built

The living half of `docs/native-ios-plan.md`, which says where this is going. The app is still the web view; since Phase 2 (#198) it needs iOS 18 and links the packages below, and native screens open over the page through a bridge.

## The packages

| Package | What it holds | Mirrors |
|---|---|---|
| `CasyCore` | Pure logic, no UI: the engine's types, Danish time (`Zone`), dates as text (`Format`), holidays, periods and the viewer's clock, `PhoneBusy`, votes and the event lists (`Events`), what a swipe on a group does and its member line (`Groups`), who can be invited, an email's look, a link's life and whom a text goes to (`Invite`) | `src/lib`, `src/types` |
| `CasyAPI` | `EdgeFunctions.call` (the web's `callFunction`), and the answers as Codable types | `src/lib/supabaseFunctions.ts`, `src/api` |
| `CasyUI` | `Theme` (colours), `casySheetBar` and `casyPushedBar` (every sheet's top bar, design rule 11), `FlowButton` (glass, or `.solid` orange for an invitation's yes), `GlassButton`, `casyGlass()`, `ListRow`, `ListAvatarRow` (a picture in front), `ListPickRow`, `ListSwitchRow`, `CasyField`, `Avatar`, `Notice`, `ConfirmButton`, the String Catalog | `src/index.css`, `src/theme.css`, `src/components/ui` |

Rules for code in them:

- Every date is Danish time, or a zone passed in. Never `Calendar.current` or `TimeZone.current`: the tests run in New York so a slip fails. The app passes in the device's zone where it matters (`yourTime`).
- Every choice between iOS 26 and earlier is made in CasyUI, never with `#available` in a screen.
- A successful answer of the wrong shape is an error, never a crash. Words a screen only displays (a provider, a status) stay strings, so a new value from the server can't stop an answer from reading.
- Dates are written from the names in `Format.swift`, not the system's formatter, whose wording changes between iOS versions.
- New copy goes into `Localizable.xcstrings` in Danish and English. A test fails on a missing language, a dash, an emoji or "iCloud".

## How a screen is ported

As a translation of its web screen, checked against the web's screenshot in the same simulator until they match: `docs/native-visual-parity.md` (#280; the screens below are being redone that way in #281). The screens below predate it and are being brought back through it.

## The bridge

`ios/App/App/Native/` is a synchronized folder: a new Swift file there needs no edit to `project.pbxproj`. `Bridge/NativeBridgePlugin.swift` and `src/lib/nativeBridge.ts` (with `NativeBridgeSync`, mounted in `AppBackground`) are the two ends.

- The web view owns the login. It lends the access token (`SessionBox`, in memory only); one about to run out is asked for again (`needSession`), never refreshed natively, as Supabase rotates refresh tokens.
- Language and theme are the web view's too: a choice made natively is sent back and applied as its own rows do. Strings follow Casy's language (`CasyStrings.language`), not the phone's.
- **The rewrite reaches people all at once, as its own update (decided 2026-11-09).** `nativeScreens` is empty in a Release build, so TestFlight and App Store builds keep the web's screens and `main` can ship fixes and features meanwhile; native screens show when running a Debug build from Xcode. The web asks once which screens exist (`useNativeScreen`), so a web build never opens one its app doesn't have.

- **The Profil list** (`Screens/ProfileScreen.swift`, Debug only until the whole sheet is native) opens from `?profile` through `profile/NativeProfile.tsx`. Indstillinger is pushed inside it; a row whose screen is still the web's closes the sheet and `closed` carries `next` (the address), so the page goes there as one step; `signOut` is the page's too, as it owns the login. The web's sheet answers `?profile=<screen>` as before, and its way back to `?profile` opens the native list again. The app never opens Safari: help pages are the page's own screens inside the app until they are rebuilt in Swift. The picture on the name card (add, crop, remove) is native too.
  - **Its look against the web (#281):** the list matches ProfileHubList in `ParityUITests` (`profile-light`, `profile-dark`), drawn with CasyUI's `CardList` and `CardRow` (the web's ListGroup and ListRow, value for value, not a SwiftUI `List`) and the web's lucide icons, Bedøm appen included. The sheet is the web's height, 85 % of the screen (`casy.stacked` in `NativeBridgePlugin.present`), with the calendar above it. Different on purpose: below full height iOS 26 floats the sheet a little inset and draws it slightly smaller (about 96 %), in its own glass (the hosting view is clear so the glass shows), where the web imitates glass; the bar is the system's, 23 points taller than the web's header, so the list starts that much up under it and the name card stands where the web's does. Because of that scale the diff's share is no measure for this sheet: compare positions in the sheet's own points (each border within a point of the web's, measured 18 Nov 2026).
- **Grupper** (`Screens/GroupsScreen.swift`) is pushed inside the Profil list: the invitations, then your groups, each swiped left to leave or delete (asked first when it takes the group from others, `groupSwipe`). An invitation opens its own screen (Bliv medlem, Nej tak, blocking the sender behind the ?); joining closes the sheet with `joined`, and the page offers notifications as its own invitation does. Lav en gruppe opens `NewGroupSheet`: the picture, name and description, Næste makes it, and the same sheet goes on to its invite.
- **A group** (`Screens/GroupScreen.swift`) is pushed from its row: the picture, name, size and age, the members (what they see behind the ?), Rediger gruppe (picture, name and description in one sheet, only what changed saved), Tid til hinanden for groups of four or more, Rapportér eller bloker (`ReportSheet`: the group or a member, why, a note, blocking and leaving with it), and leaving or deleting, asked first. Left or gone from elsewhere, it goes back to Grupper, though only once a sheet over it has closed.
- **Inviting** (`Screens/InviteSheet.swift`, `InviteModel`) is the web's InviteBody: from the contacts (`ContactInviter`: iOS's picker, then Messages, or the share sheet on a phone that can't text; what is picked never leaves the phone), by email, a link with copy, share and its QR code (Core Image), and the people from your groups and friends ticked (`knownPeople` in CasyCore), folded past four. After an invite the page is sent `inviteSent`, so its home page's nudge to invite people goes as after its own. Not yet: the notifications ask the web makes after sending (the push ask is Native 4's).
- **Venner** (`Screens/FriendsScreen.swift`) is pushed from Profil: everyone you share a group with or once did, each with where from, and Fjern for a friend from a group since gone only (anyone else would come back). Tilføj en ven is the invite sheet made for a friend (`InviteModel.forFriend()`): the contacts and a link, no email and no people.
- **Slet konto** (`Screens/DeleteAccountScreen.swift`) is pushed from Profil: what goes and what stays, then the word typed before the red row deletes. The page is sent `accountDeleted`, drops its login on this device only and opens the sign-in page saying the account is gone, as the web's DeleteAccountSection does.
- **Dine data** (`Screens/MyDataScreen.swift`, `MyDataModel`) is pushed from Profil: everything the web's MyData lists, in its order and words, read fresh each time; the AI switch at the top while it is off and in the AI list once on (turning it off asks first); blocked people with Fjern blokering; and Hent en kopi, the export written to a JSON file for the share sheet. Two things live in the page, so the bridge asks it: the labels kept on this phone (`needPhoneFacts`, answered by `phoneFacts`), and what a no to the AI deletes there (`aiConsent`, which runs the page's own `afterAiConsent`). The privacy policy's links open the page's Privatliv inside the app. Not ported: the testers' labelling and trip rows.
- **Admin** (`Screens/AdminScreen.swift`, `AdminModel`) is pushed from Profil for an admin: health, the numbers and the AI's use per skill, then groups, users and calendar health under one switch, searchable, the last two filterable to problems. A group opens to its members (swipe to remove, asked first) and a red row that deletes it for everyone; a user, never yourself, opens to their facts, the AI tester switch, a calendar sync and deletion behind their typed name; a connection syncs from its row. Each action patches the list at once, then reloads. Under its health, Rapporter and Rettelser til AI'en (`Screens/AdminReviewsScreen.swift`, `AdminReviewsModel`) each push a screen of what waits for review, never who sent it: a report can be marked Klaret, have its picture taken down, or have its group deleted (asked first); a correction says what the AI said and what came of it, wrong ones first, and Håndteret deletes it. Beside them the push test switches notifications on through the web view and sends one through Apple. The fake server's `{ reviews: true }` reset seeds the made-up ones in `e2e/adminReviews.ts`.
- **Help pages** (`Screens/HelpScreens.swift`): Hjælp og kontakt, Sådan virker det, Vilkår and Privatliv are pushed inside Profil, laid out from CasyUI's `HelpPages.json`, the web pages' own words in both languages. `e2e/helpPages.parity.ts` writes it from each page's exported `COPY` and fails when a page changes until it is written again (`UPDATE_PARITY=1 npx vitest run e2e/helpPages`), so the app's legal text can't drift from the site's. A link in their text (and Dine data's) opens the page it names in Swift (`pageLinks`, `PageLink`), Mail for an address, the web's page inside the app for one not yet ported (the calendar guides), and a site outside is plain words: the app never opens Safari.
- **Aftaler** (`Screens/EventsScreen.swift`, `EventsModel`, #199) opens from the home page's Aftaler button (`NativeEvents`, sharing `useNativeSheet` with `NativeProfile`): Svar nu, Kommende and Tidligere as `phoneEventGroups` sorts them, each row its `DateTile`, name and group; a row to come swipes to Aflys (your own, asked first) or Forlad. A vote to answer hands over to the home page (`?vote=<id>`), still the page's until the home page is native (#201). A vote you have answered pushes `VoteScreen`: its dates ranked by yeses, each with the faces of those who can (a tap opens who said what) and your own answer as a cross and a tick, Vælg on each when no date can win and it is yours to choose, the time left (`Countdown`) or that it waits for everyone, the suggester's Påmind, Svarfrist (a sheet of none or 1 to 7 days) and Afgør nu (asked first), then the place and note, Rapportér aftalen and Aflys or Forlad. Søg igen hands over to the page's own vote screen (`?events=<id>`), where it lives with Planlæg. An agreed event pushes `DatedScreen`: its date tile and time (and the viewer's own clock where it isn't Danish time), everyone's face with where they stand (`PeopleRow`, the suggester starred), its place and note, then Kan ikke alligevel (an agreed vote), Rapportér aftalen (`ReportSheet(event:)`) and Aflys or Forlad, each asked first. Tilføj til min kalender is pinned along its bottom (`Screens/AddToCalendar.swift`, as the web's AddToCalendar `flow`): straight into the primary calendar, or a choice of the calendars Casy may write to (which becomes the primary), or a calendar file through the share sheet; an event bound for this phone's own calendar is written by the page (`needPhoneWrite`, answered with `phoneWritten`, as its own `syncPhone`), then the list is fetched again. Above the faces is the slice of your own day around it (`Screens/DaySlice.swift`, the web's DaySlice): calendar-busy for that day, this phone's own calendars read from the phone with their titles and Apple's colours (its calendars are those whose EventKit ids are here), what you told Casy and the Danish holidays, laid out by CasyCore's `CalendarDay.swift` (`segmentByDay`, `calendarColors`, `withPhoneEvents`, `placeBlocks`, `tint` and `shade`, kept equal to the web's by `calendarDay.cases.ts`), the event solid in orange; a tap opens the day view, still the page's (`?day=`). Stored event names ("Evening") read in the reader's language through `CasyStrings.eventTitle`, kept equal to `STORED_TITLES` by `eventTitles.test.ts`. Every rule reads `Native.now`, which a UI test fixes with `-casyNow` to the fake backend's moment.
- **Kalendere** (`Screens/CalendarsScreen.swift`, `CalendarsModel`, #200) opens from the home page's Kalendere button (`calendarView/NativeCalendars.tsx`), on the screen the address names (`?calendars=accounts`, `=tour`; `connect=apple` opens that form). The page keeps three things on this phone that Kalendere reads and changes: the holidays' tick, the calendars the guided setup has been through, and this phone's own connection. They go with `open`'s `state`, and come back as `calendarPrefs`; every change to your calendars sends `calendarsChanged`, on which the page fetches its calendar answers again. The list is calendar-busy over the months searched, grouped by brand (`groupCalendarsByBrand`), each group folded until opened, a calendar's category and priority as system menus (with Ny kategori, `NewCategorySheet`) and renaming behind its pencil; an unticked one waits under Tæller ikke med. Forbundne kalendere (`Screens/ConnectedCalendarsScreen.swift`) is pushed inside it: with nothing connected, the one Importér min kalender with its picture (`OnlyTimesDemo`); the accounts with Synkronisér nu and removal (asked first); this phone, or folded away an Apple account (`AppleFormSheet`, the password's shape checked once pasted or sent) or a link (`LinkFormSheet`); and Primær kalender (`PrimaryCalendarScreen`, a change asked first) with Tilføj automatisk. The phone's calendars are read and sent by the page (`needPhoneSync`, answered with `phoneSynced`, up to two minutes for iOS's own question), and removing this phone tells the page to forget it (`phoneForgotten`). The guided setup (`Screens/CalendarTourScreen.swift`) goes through the calendars wanting a look one card at a time, saving behind it, and ends in a fan and `Confetti` (CasyUI). The rules are CasyCore's `Calendars.swift`, kept equal by `calendars.cases.ts`. A UI test opens one of its screens with `-casyOpenScreen calendars:accounts` and answers for the page with `-casyPhoneSync <synced|denied>`; the fake backend starts with nothing connected after a reset with `{ "calendars": "none" }`.
- **Tilføj til kalender** (`Screens/TellScreen.swift`, #200) opens from the plus on My calendar (`tellCasy/NativeTell.tsx`): a box to write or speak in, what the AI made of it (`entries-ai`) with each entry left out by its cross, more details or starting over, and Gem pinned along the bottom; kept, the sheet closes with `added` and the page glides the month to its first day. What is kept already is listed under with a delete (calendar-busy's entries, through `CalendarsModel`). Before the first ask the AI's yes is checked (`aiConsentGate`, `aiContentAllowed`) and asked for with `AiConsentSheet` (`Screens/AiConsentSheet.swift`, its four pages), which tells the page through `aiConsent` as Dine data does. Speech is native (`Native/Speech.swift`, `SpeechInput`): iOS 26's `DictationTranscriber` on the phone, `SFSpeechRecognizer` before that, the transcript kept across pauses by CasyCore's `hearSpeech`; under a UI test it never listens. `entryWhen` and `hearSpeech` are kept equal by `calendars.cases.ts`.
- **A trip's sheet** (`Screens/TripScreen.swift`, `TripModel`, #200) opens from a trip's bar on My calendar (`trips/NativeTrip.tsx`). Finding trips and keeping the answers stays the page's (`useTrips`, on this phone) until the home page's background work is native, so the page sends the trip as `open`'s `state.mark` and again with `setTrip` after each answer, and carries out each answer the sheet sends (`tripAction`: accept, decline, home, return, outbound, addToCalendar, which answers with the calendar's name). The sheet shows the journeys and the time away with Ja, det passer or Nej; an accepted one's Læg i min kalender and Slet rejsen; where home is, as a row per city; or when you are back or left, on a month (`DayPicker`, the journey's day marked and the stretch away shaded). CasyCore's `Trips.swift` holds the types, `cityName` and `dayOptions`, kept equal by `calendars.cases.ts`. A UI test opens it on a made-up trip with `-casyTrip <trip|return|home>`, and the test launch answers for the page. A sheet's title too long for one line now takes two beside the close button (`casySheetBar`).
- **Tid til hinanden** (`Screens/PrimeDateScreen.swift`, #200) opens from a starred day (`calendarView/NativePrimeDate.tsx`), which the page still finds (`usePrimeDates`) and sends as `state.prime`: the group (fetched here), the day and its free time (`stretchShape`), everyone named with you last (`everyone`), and the promise as footnote. Planlæg closes it with `plan`, and the page opens its own Planlæg with the group and the day set, until Planlæg is native (#201). A UI test opens it with `-casyPrime <group id>`.
- **The small asks** (`Screens/AsksScreens.swift`, #200): the page still decides when each comes, and opens it natively when the app has it. The AI's question on My calendar (`aiConsent`, `AiConsentPrompt`) is `AiConsentSheet` on its own; either answer is final, as on the web. The push ask (`push`, `PushAsk`, its `state.reason`) has one button that turns notifications on through the page (`enablePush`), can't be swiped away, and can only be put away (Ikke nu) after that failed. An app too old (`update`, `UpdateRequired`, `state.storeUrl`) is full screen with no way out but the App Store app. A UI test answers iOS with `-casyPushAnswer <granted|denied|failed>`; `casySheetBar` with an empty `close` has no button.
- **The home page** (`Screens/HomeScreen.swift`, `HomeModel`, `NativeHome.swift`, #201), behind Admin's "Native forside" (`NativeHome.on`, this phone's UserDefaults, Debug builds only). It is a child of the web view's controller, over the page's own home page, and reads your calendar itself: the busy times over the year searched, this phone's events with titles (`DayOfCalendar.phoneDrawn`), laid out a month at a time off the main thread (CasyCore `Month.swift`: `calendarItems`, `monthLayout`, `layoutWeek`, kept equal to `monthItems.ts`, `calendarOverview.ts` and `monthGrid.ts`). The page still works out the votes' dates, the trips, the starred days and the vote pill, and sends them with `setHome` (`useNativeHome`), with `covered` while something only it draws is over the month (the day view, Planlæg, a vote, the import card, the agreed card), when the native page steps aside. Each press comes back as `homeAction` and is done as from the page's own buttons. A UI test plays the page with `-casyNativeHome YES`.
  - **Its look against the web (#281):** the month matches the web's in `ParityUITests` (`home-month-light`, `home-month-dark`), its icons the web's lucide ones (`LucideIcon`, CasyUI's `Icons.xcassets` written by `scripts/native/lucide-icons.mjs`), its counts the page's (`badges` in `setHome`: Kalendere, Aftaler, Profil). Different on purpose: the capsules are real Liquid Glass, and on iOS 26 what scrolls under the header is softened by the system's scroll edge (`casyTopBar`); at rest the header is the page's own colour, as the web's, never a grey band. The day view matches the web's DayView and DayColumns (`home-day-light`, `home-day-dark`): the week row's one capsule under the days in view, the names row with the week number, the whole days, hour lines from the gutter, the blocks' inner bar and clock, the time now in the gutter. One toolbar floats over the month and the day view alike (`HomeScreen.toolbar`, the web's HomeToolbar), on its MORPH spring: it becomes the day's 40 % into the zoom and the month's as closing starts; the left capsule's width morphs while Kalendere and "‹ <month>" crossfade in place, and the right capsule's buttons keep one layout (the 1/2 day switch laid out left of the plus and I dag) while only a capsule-shaped window onto it, with the glass behind, widens and narrows, so nothing slides over anything. The zoom runs on the web's curve (380 ms out, 320 back), its fade's timing on the fade alone (`animation(_:body:)`). Two differences from the web, asked for on 18 Nov 2026: the day view grows out of the date's 32 point circle and shrinks back into it, its corners rounding until it is that circle (the web zooms into the whole cell, square); and in the week row the selection turns to glass while it moves, after a weather app's slider (`casyGlass(in:tint:)`, frosted before iOS 26): when the day changes within the week, the day's circle becomes a clear lens where it stands (faintly tinted its colour, a soft shadow), swells, glides to the new date and turns back into that date's circle, which never shows before it arrives (`settled`); plain colour at rest. Each day is cut from your calendar once, off the main thread, as it loads (`HomeModel.byDay`), and kept laid out (`dayCache`), so a swipe only looks days up; the names and whole days rows slide with the hours by following the pager's offset (`DayPager`), and only a jump (a number, a week, I dag) moves the hours, to the web's opening (`openingOf`). The web's own opening position varies between runs (07:30 or about 07:50 for the same day); Swift's follows its rule. Each month is two scroll targets, its short name (id `-month`) and its weeks (id `month`), so a month opens on its first week with the name under the header, and the title follows the web's rule (`track` in `MonthView`).
- `GroupsModel` keeps the Profil row's count, and every change sends `dataChanged`, on which the page fetches its groups, invitations and blocked people again.

## What keeps it equal to the web

| Kept equal | Written by | Checked in Swift by |
|---|---|---|
| The engine | `src/lib/parity/*.cases.ts`, `parity.test.ts` | `CasyCoreTests` (`Parity/*.json`) |
| The API's answers | `e2e/apiAnswers.parity.ts`, from the browser tests' fake backend | `CasyAPITests` (`Answers/*.json`), each read and written back with nothing lost |
| The colours | `src/lib/parity/theme.test.ts`, from the stylesheets | `CasyUITests` (`Fixtures/colors.json`) |

Change a rule in TypeScript and Vitest fails until the files are written again, then the Swift tests fail until Swift changes too:

```bash
UPDATE_PARITY=1 npx vitest run src/lib/parity e2e/apiAnswers
```

The fake backend is not the real server: a screen's first run against the live functions is still the real test.

## Running the tests

Never run `swift build` or `swift test` in the repo without `--scratch-path` outside it (iCloud, see the plan).

```bash
TZ=America/New_York swift test --package-path ios/Packages/CasyCore \
  --scratch-path ~/Library/Developer/Xcode/DerivedData/CasyCore-scratch
scripts/native/snapshots.sh            # CasyUI's pictures; --record draws them anew
```

CI's `native.yml` tests all three packages on a Mac (CasyUI through `xcodebuild`, as its Xcode's plain `swift test` doesn't compile the String Catalog) and builds them for the iOS simulator, whenever `ios/Packages` or `src/lib` change.

The app's UI tests (`ios/App/AppUITests`, a synchronized folder) open native screens signed in, against the browser tests' fake backend over HTTP (`scripts/native/fake-backend.ts`; a test that changes its world calls `POST /reset` first), locally: for each step only the screens it touched (`-only-testing:AppUITests/<Class>`), the whole suite every three or four steps and always before a merge; and on CI (`ios.yml`) on `main` only, after the merge, so a merge doesn't wait the 9 minutes they take on GitHub's Mac:

```bash
scripts/native/ui-tests.sh             # UI_TEST_DEVICE picks the simulator
```

A Debug build reads the launch arguments that make this possible (`TestLaunch.swift`: `-casyBackend`, `-casyOpenScreen`, `-casyPushPermission`, `-casyLang`), and then ignores what the web view sends. A Release build has none of it. Each new screen gets its tests here: both bugs found by hand in Notifikationer (the section never loading, a switch waiting for the server) are the kind they catch. `Info.plist` allows local networking so the app can reach the fake backend; it opens nothing else.

The snapshots (`CasyUISnapshotTests`) check layout, colours and words on the pinned simulator (iPhone 17, iOS 27.2), and are not on CI: its Xcode has an older iOS. They are drawn off screen, where **Liquid Glass doesn't show**, so glass is judged on a real phone.
